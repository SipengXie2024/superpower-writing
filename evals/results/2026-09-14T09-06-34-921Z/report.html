### A 组｜这就是你要做的那篇：12 + 15 + 2 合成一篇

## 三、前两名为什么是前两名，以及第 3 周的决策点

**第 1 名（9+1）赢在"即使假设是错的也有结果"。** revmc 已经存在，archive 快照给你真实 replay，baseline 明确（revmc 全量 AOT vs revm 纯解释器），指标明确（回放墙钟时间、编译开销摊销点、常驻内存）。做完一定有一张图。会议形状也最对——这是标准的 ATC 论文。

它的 Novel=3 而不是 4，因为按 novelty rubric，"把已知方法搬到新场景"本身封顶就是 3。要抬到 4，得让**EVM 特有的那部分**承重，我看到两个真实的抓手：

- **gas 计量和墙钟时间是解耦的**。编译让执行快 5 倍，gas 账一分不变。JVM 没有这个对应物，它直接影响 tiering 策略该优化什么——这是个 JIT 文献里不存在的约束。
- **合约不可变、按 codehash 内容寻址**。编译产物可以跨节点缓存甚至分发，没有 class loading / 失效问题。这意味着"编译开销"在网络层面是一次性的，而第 1 条整条的前提（编译开销 vs 命中率的平衡点）在这个观察下要重算。

把这两点写进 intro，这篇就不是"我们把 JVM 那套搬过来了"。顺便：evmjit 当年失败的原因正是"全量编译，编译时间超过执行时间"，这是你 motivation 段现成的历史素材。

**第 2 名（12+15）赢在便宜，输在新颖性风险。** "历史区块并行度上界"这类测量我印象里已经有人发过 `[UNVERIFIED]`，这是它排第二的唯一原因。但你的第 15 条其实离一个真正的机制只差一步：不要停在"哪几类协议在拖后腿"，要走到**"是哪几个具体的存储槽在拖后腿，以及可交换性（commutativity）能不能把它们拆掉"**。余额更新本质是可交换的增量，但 EVM 把它当 read-modify-write，这在热点 ERC-20 槽位和 DEX 储备槽上制造了假依赖。数据库那边这是老思想（escrow transaction、Doppel 的 phase reconciliation `[UNVERIFIED]`），搬到区块链执行上、并且**用真实主网 trace 给出证据**，这才是 EuroSys 形状。停在测量就是个短文。

**第 3 周的决策点（这是你组会上最该讲的一句话）：**

> 先花 3 周做第 8 条（缩小版），让数据来选第 1 还是第 2。

因为没人知道答案：如果回放时间被解释器 dispatch 主导 → 走 9+1；被 state 访问主导 → 走 4 或 11；已经是并行度受限 → 走 12+15。现在在会上投票选主线，是在猜一个 3 周就能测出来的数。

**关于第 8 条本身两个技术意见：**
- **别在 geth 上做。** Go 的 goroutine 调度和栈管理让 uprobe 级别的细粒度归因很难做对；eBPF 看 syscall / block layer / page fault 很好，但把 stall 归因到"EVM 层的某次 state 访问"需要用户态插桩。你是 revm 栈，直接测 revm/reth，代码在你手上。geth 留着做交叉验证就行。
- 这条正好是给本科生的活：回放语料 + 剖析 harness，边界清楚、不阻塞主线、做砸了也不致命。

**第 11 条是条件性的**，别现在决定。如果第 8 条测出 journal/revert 占执行时间不到 5–10%，这条就是在优化一个非瓶颈（F4），直接毙。另外——**MHOT 我没能确认指的是哪篇**，HOT (Height Optimized Trie) 我知道，MHOT 没对上号。你确认一下，这直接影响它的 Novel 打分。

**第 5 条（跨 L2 MEV 传导）——数据不存在，不是我们不想做。**

> 「各家 sequencer 的**内部**私有 mempool 排序日志不是公开数据。Base 根本没有公开 mempool，交易直接进 sequencer；Arbitrum、OP 也都不发内部排序日志。这不是调 RPC 能拿到的，得跟运营方谈合作。但**出块后的顺序是公开的**——如果改成用公开 L2 出块顺序加上 L1 结算交易反推传导路径，这条马上可做，我排到第 4。只是它的会场是 IMC / FC 那一挂，不是 EuroSys。」

**第 2 条（Block-STM 静态重排）——这条我要当面纠一个语义问题，措辞得稳。**

> 「Block-STM 之所以能并行，是因为它**保持**了区块内的确定性提交顺序；L1 上交易顺序是共识关键、直接决定 state root，validator 端重排会算出不同的根。所以'静态重排降 abort 率'在 validator 侧不成立。但在 **builder / sequencer 侧**成立——顺序本来就是它选的。改成'sequencer 在保证优先费排序和 bundle 原子性的前提下，选一个并行度最大的顺序'，这是个有约束的优化问题，而且 Base 是单中心化 sequencer，是现成的实验平台。这么改我排第 3。」

**第 7 条（从零预训 7B）——用算术挡，不用品味挡。**

## 为什么是这个顺序：三条线

### 主力线：8 → 9(吞掉 1) → 13

**为什么 8 排第一**：你列表里有五条（1、4、9、11、12）都隐含同一个假设——"EVM 执行的瓶颈在 X"。8 是唯一一条能证伪这个假设的。花三周把数拿到，后面四个月不会押错。**这是"先测后做"，不是"先热身"**，这个话术在组会上很好讲。

一个技术坑要提前说：**geth 是 Go，eBPF uprobe 打 Go 很容易出事**——Go 1.17 之后的寄存器 ABI、goroutine 栈搬迁，uretprobe 挂 Go 函数是出了名的会崩。建议分两层：进程外的 IO / page fault / 块设备延迟用 eBPF（安全且准），进程内的归因用 Go 自带的 runtime/trace + pprof。更好的做法是**主目标换成 reth**，Rust 上 uprobe 干净，而且你后面的工作全在 revm 上，geth 留作交叉验证。

**为什么 9 是旗舰，而 1 只是它的第一个实验**：1 和 9 本质是同一件事的静态版和动态版，1 单独拿出去是 workshop 体量。9 撑得起一篇 ATC，理由是它**不是"把 JVM 那套搬过来"**，四个差异点都是真问题：

- **误编译在 EVM 里等于共识分裂**，不是"程序跑错了"。所以分层策略必须在一个正确性预算下做，gas 计量和异常halt 要逐字节等价。这直接把 13 从"可选的差分测试"变成系统的一部分——审稿人一定会问"你怎么保证 JIT 不会导致链分叉"，13 就是答案。
- **热度的 key 不是地址，是 codehash**。EIP-1167 最小代理和 diamond 模式下成千上万个地址共享一份代码。你第 1 条写的"调用频次前 1% 的合约"，按地址统计会把结论算歪——代理合约本身是超热的，但它的代码只是个 delegatecall 桩。这一条会直接改你的实验设计，越早改越好。
- **同一份 codehash 在全网所有节点上都一样**，所以编译产物是可以内容寻址、跨节点共享、甚至随客户端预置分发的。这是 JVM 世界不存在的结构，也是我看下来这篇里最有意思、还没人认真写过的点。
- **workload 是外部驱动且高度可预测的**：热合约几个月不变，所以持久化的 profile 缓存跨重启有效，不像长驻 JVM 那样每次都要预热。

### 第二线：12(吞掉 15) + 2 —— 交给本科生，瞄 EuroSys 春季轮

12 单独做是**复现**：Saraph & Herlihy 2019 就测过以太坊的投机并发上界，后面还有若干跟进。纯做一遍投不出去。新意必须来自三处，而这三处恰好就是 15 和 2：

1. **L1 vs L2 对比**——你有 Base RPC，这是 2019 年那批工作没有的；
2. **15 的按协议拆解**——我的预判是上界会被极少数热 slot 卡死（WETH 余额槽、头部 AMM 的 reserve、USDC 余额），也就是说"是哪几类协议在拖后腿"这个问题的答案可能是"是哪几个 storage slot"。这个结论如果成立，比"上界是 3.2x"有意思得多；
