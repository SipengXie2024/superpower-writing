\subsection{Hotspot Selection}
\label{sec:method:hotspot}

Our compiler tier is built on revmc, which lifts the bytecode of a hot contract
to native code while the node is running. The unit of translation is the EVM
basic block: \texttt{translate\_block} walks the decoded instruction stream of
a block and emits, for each opcode, IR implementing that opcode's semantics
inline, rather than a call back into an interpreter handler. Once a contract
has been lifted, a call into it no longer steps an interpreter loop; control
enters the generated function and the opcode bodies are laid out as
straight-line native code, so the per-instruction dispatch performed by the
interpreter disappears entirely. Compilation is transparent to the rest of the
node: the generated code presents the same interface to the host as the
interpreted path, and execution falls back to the interpreter for any contract
that has not been compiled.

Dispatch, rather than arithmetic, is what an EVM interpreter spends most of its
time on, which is what makes this transformation worthwhile. Executing one
opcode on the interpreted path costs a bytecode fetch, a bounds check, an
indirect branch through the handler table, and the stack-depth and gas
bookkeeping that surrounds it, while the opcode's own semantics are frequently
no more than a few operations on a 256-bit word. The indirect branch is
additionally hard to predict, because its target is determined by contract
bytecode for which the predictor has no useful history, so part of the cost is
paid in pipeline stalls rather than in retired instructions. Measurements of
interpreted EVM execution attribute the bulk of the per-instruction cycle count
to this dispatch overhead, making it the dominant cost in EVM
execution~\cite{evm-dispatch-2023}. Removing it is therefore the largest single
lever a compiler tier has --- but it is a lever that only pays off on code
executed often enough to amortize the cost of translation, which is what makes
selective compilation, rather than blanket compilation, the right design.

We select hotspots at the granularity of whole contracts. Gas consumption on a
production chain is heavily concentrated: over the most recent 100{,}000 blocks
of Base mainnet, the 50 contracts consuming the most gas account for 78\% of
all gas consumed network-wide.

A compiled-code cache holding a few tens of entries therefore covers the
majority of the execution a node performs, keeping both compilation time and
cache footprint negligible relative to the execution time saved. Contract
granularity also matches the structure of the EVM itself: deployed bytecode is
immutable and content-addressed by its code hash, so a compiled artifact can be
keyed by code hash, reused across every call site and every block that touches
the contract, and never invalidated. Finer-grained units, such as individual
functions or traces, would add little, since the concentration that motivates
selection is already visible at contract granularity, and would forfeit the
invalidation-free caching that the code hash makes possible.
