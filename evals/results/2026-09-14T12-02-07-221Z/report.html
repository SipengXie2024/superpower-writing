## A. EVM 执行引擎（工业实现）

| 条目 | 做了什么 |
|---|---|
| **geth `core/vm`** | Go 的 switch/jump-table 解释器，逐 opcode 查 handler，无任何编译路径；事实上的规范实现。 |
| **evmone (baseline)** | C++ 解释器，部署时一次性做 jumpdest 分析，用 computed goto 压掉 dispatch 开销。 |
| **evmone (advanced)** | 把字节码切成 basic block，在块入口一次性做 gas 扣减和栈高度检查，省掉逐指令边界判断；走哪档是构建/配置期决定的。 |
| **evmjit** (Bylica, ~2016) | 最早的 EVM→LLVM IR→native 编译器，按 code hash 缓存产物；**名字叫 JIT，但首次执行即编译，无分层无 profile**。这条必引。 |
| **revm** | Rust 解释器，reth / Foundry / 绝大多数模拟器的底座，当前事实标准。 |
| **revmc** | revm 的 LLVM 后端，AOT 与"JIT"两模式，但编译时机由调用方显式触发。（你已有） |
| **EVMC** | 客户端与 VM 之间的 Connector ABI。值得引——它正是"把另一档执行器挂进现有客户端"的现成接口，对你的可部署性论证有用。 |
| **Hyperledger Besu / Nethermind / ethereumjs** | 分别跑在 HotSpot / RyuJIT / V8 上的 EVM 实现。见 §F 第 4 条，这三个是"first"最脆的受力点。 |
| **eEVM** (Microsoft) | 为 CCF 机密计算写的 C++ EVM，解释器。 |
| **EIP-3540 / EOF** | 部署期完成代码验证与代码-数据分段，消除动态 jumpdest——直接降低原生编译难度，是你"生态正在往可编译方向走"的论据。 |
| **zksolc (zkSync Era)** | Solidity/Yul → LLVM IR → EraVM 字节码，是 EVM 语义走 LLVM 的另一条工业路线。 |

## F. 会被拿来打 "first" 的四条，以及怎么挡

不是劝你改句子——是你正文里最好主动把这四条摆平，省得进 rebuttal。

1. **evmjit** —— 它名字里就有 JIT。**区分线**：首次执行即编译、按 code hash 缓存，编译决策与调用频次无关，没有第二档也没有降档。
2. **EOS VM 的三档（interpreter / JIT / OC）** —— **区分线**：不是 EVM；且档位由部署配置决定而非运行时热度计数器 `(这条的提升触发条件我没把握，建议核一下再落笔)`。
3. **Arbitrum Stylus 的 cache manager** —— 这条最危险，因为它同样是**用链上信号决定谁留在快档**。**区分线**：目标是 WASM 不是 EVM，而且谁留在缓存里靠竞价这个经济机制，不是调用频次 profile；它管的是"编译产物驻留"，不是"是否提升"。建议在 related work 里单独给它一两句，别混在 WASM 那一堆里一笔带过。
4. **Besu / Nethermind / ethereumjs 从宿主 JIT 白拿分层** —— 一定会有 reviewer 说"Besu 上的 EVM 早就享受 HotSpot 的 tiered + profile-guided 重编译了"。**区分线（这条我建议直接写进 intro 或 related work 开头）**：宿主 JIT 优化的是**解释器分发循环本身**，profile 的粒度是 Java/C# 方法，不是合约；它无法按合约特化、无法把 immutable 常量折进代码、无法跨 opcode 消掉栈进出。你的贡献是**把分层的粒度放在合约字节码这一层**。这个反驳是硬的，摆出来只会让 "first" 更站得住。

先说两句跟 "first" 无关的事——是那句话里的两个事实问题，抠掉反而让对比更锋利：

- **evmone 的 advanced 模式不产原生码。** 它做的是基本块级预分析（把 gas 扣减和栈深检查提到块入口），然后跑一份 threaded-code 表示，本质还是解释器。把它跟 revmc 并列成 "ahead-of-time native compiler"，懂 EVM 的审稿人一眼就看出来。

- **最可能被当成撞车抛出来的是 evmjit**（Bylica，2016，cpp-ethereum 那套 LLVM JIT，按 code hash 缓存编译结果）。它是"首次执行即编译 + 缓存"，没有分层、没有 profile、没有运行时提升。你那句话把世界分成"解释器 / AOT"两类，evmjit 是第三类，不在里面——补一句把它显式归位，这个口子就堵上了。

## 一、EVM 执行引擎（工业实现）

1. **go-ethereum `core/vm`** — switch 分发的字节码解释器，事实上的参考实现和正确性基准。
2. **revm** — Rust 写的 EVM 解释器，Reth 和 Foundry 的执行内核，无编译路径。
3. **evmone baseline** — computed-goto 分发解释器，执行前跑一遍分析，建 jumpdest 表并校验栈需求。
4. **evmone advanced** — 基本块粒度预计算 gas 与栈边界、生成 threaded code 的解释器；走哪档由构建/配置静态决定，与执行热度无关。
5. **evmjit**（Bylica, 2016）— 基于 LLVM 的 EVM JIT，按合约 code hash 缓存原生码，已弃用；"EVM 上跑过 JIT"的历史前例。
6. **revmc** — 用 LLVM/Cranelift 把 EVM 字节码编译成原生码，提供 AOT 与 JIT 两种模式，无运行时 profiling 与层级提升。
7. **Besu / Nethermind** — JVM 与 .NET 上的 EVM 实现；宿主运行时自己有分层编译，但分层作用在解释器循环上，EVM 层面没有。**这条值得单独写一句**，它正好说明"寄生于宿主 JIT"和"在 EVM 语义层做分层"是两回事。
8. **Erigon / Silkworm** — 前者 geth 派生 EVM，后者直接用 evmone；说明生态里执行引擎高度收敛到上面几套。
9. **Monad** — 并行 EVM，公开材料提到过编译式执行路径。`[待核]` 我对它是否真落地了编译器没把握，但这是审稿人最可能点名的工业项目，建议你亲自确认口径再写。
10. **EOF（EIP-3540 / 3670 / 4200 / 4750）** — 容器格式加静态相对跳转，消灭动态 jump。**这条对你是结构性的**：它决定了"能不能 AOT"这个前提正在变化，不提会显得没跟上。

## 二、EVM 执行性能的学术工作

11. **Forerunner**（SOSP 2021，Chen et al.）— 基于约束的投机执行加记忆化，加速以太坊交易执行；顶会系统论文里最贴近你的一篇，必引。
12. **Block-STM**（PPoPP 2023，Gelashvili et al.）— 乐观并行区块执行，你已有。
13. **Dickerson, Gazzillo, Herlihy, Koskinen**（PODC 2017）— 给智能合约加并发，矿工投机并行执行再生成可串行化调度；并行那条线的学术源头，跟 Block-STM 配成一段。
14. **Broken Metre**（NDSS 2020，Perez & Livshits）— 实测 gas 与真实资源消耗严重脱节。**对你有用**：说明 gas 不是执行时间的好代理，所以 profile 必须打在真实开销上而不是 gas 上。
15. **Gigahorse**（ICSE 2019）/ **Elipmoc**（OOPSLA 2022，Grech et al.）— 从 EVM 字节码反编译出 CFG，专门处理动态跳转下的控制流恢复；你的编译层要做的分析和他们是同一个问题。
16. **GASOL**（TACAS 2020，Albert et al.）— EVM 智能合约的 gas 分析与优化。
17. **ebso**（Nagele & Schett）— EVM 字节码超优化器，基于 SMT 求最优等价指令序列。`[待核]` 我记不准发表场地，可能是 workshop 或 arXiv。
18. **Oliva, Hassan, Jiang**（EMSE 2020）— 实证研究以太坊合约生态，发现极小比例的合约吃掉绝大多数交易。
19. **Kiffer, Levin, Mislove**（IMC 2018）— 分析以太坊合约拓扑，同样给出调用高度长尾/集中的证据。

> 18 和 19 是我这份清单里对你最值钱的两条。你的整个设计前提是"链上调用频率有热点"，这两篇把这个前提从直觉变成引用。related work 里可以不给它们多少篇幅，但 motivation 那节应该拿它们撑一段。

## 三、其他区块链虚拟机

20. **Move VM**（Blackshear et al., Diem/Move 白皮书）— 带资源类型的栈式字节码虚拟机，解释执行，Aptos 与 Sui 共用其血统。
21. **Solana rBPF** — SBF（eBPF 派生）虚拟机，同时提供解释器和 x86 JIT，部署时编译并缓存，非热度驱动。
22. **CKB-VM** — RISC-V 虚拟机，提供解释器 / 汇编解释器 / AOT 三种执行模式，选哪种由配置静态决定。**结构上跟你最像的反例**：多档齐备，但没有运行时提升。
23. **PolkaVM** — RISC-V 指令集的合约虚拟机，线性扫描重编译到原生 x86-64，定位是 wasmtime 的替代。
24. **Substrate / Polkadot** — wasmi 解释器与 wasmtime(Cranelift) 两条执行路径并存，选择受确定性要求约束而非性能。

28. **ewasm / Hera / evm2wasm** — 已放弃的 Ethereum-flavored WASM 路线，是"换执行底座"这条路的反面教材，一句话带过即可。

31. **Arnold et al.**（Proceedings of the IEEE, 2005）— 虚拟机自适应优化综述，当伞形引用用。
32. **HotSpot**：Paleczny, Vick, Click（JVM Symposium 2001）server 编译器 C2；Kotzmann et al.（TACO 2008）client 编译器 C1；C1+C2 合并的 tiered compilation 在 JDK 7/8 落地。
33. **IBM J9 / Testarossa**（Suganuma et al., OOPSLA 2001）— 采样 profiler 驱动的多级编译（cold→warm→hot→scorching），多档而非两档的先例。
34. **Fink & Qian**（CGO 2003）— 基于 on-stack replacement 的自适应重编译。**对你是设计问题不是背景**：EVM 单次调用里有没有长循环值得 OSR，还是只在调用边界提升就够，你正文里最好表态。
35. **Dynamo**（PLDI 2000，Bala, Duesterwald, Banerjia）— 二进制层面识别热路径并动态优化。
36. **HotpathVM**（VEE 2006，Gal, Probst, Franz）与 **TraceMonkey**（PLDI 2009，Gal et al.）— trace 粒度而非方法粒度的分层提升。
37. **PyPy 元追踪**（ICOOOLPS 2009，Bolz et al.）— 追踪解释器本身而非用户程序。
38. **Truffle/Graal**：Würthinger et al.（Onward! 2013）"One VM to Rule Them All"；（PLDI 2017）自优化解释器的部分求值。
39. **V8** — Ignition 解释器 → Sparkplug 基线编译器 → Maglev 中层 → TurboFan 优化编译器的四级阶梯，按调用/反馈驱动 tier-up；主要靠官方博客引。
40. **JavaScriptCore** — LLInt → Baseline JIT → DFG → FTL 四层，Pizlo 的 "Speculation in JavaScriptCore" 是标准引用来源。
41. **.NET CoreCLR tiered compilation** — 调用计数触发 tier-up，配 OSR 处理长循环。
42. **Copy-and-Patch**（OOPSLA 2021，Xu & Kjolstad）— 接近解释器成本的代码生成，CPython 3.13 的 JIT 即基于此。**对你是候选实现**：第一档想要"编译快过执行省"时，这是现成答案。
43. **Ertl & Gregg**（PLDI 2003 及 JILP 2003）— 解释器分发机制与间接跳转预测的性能分析；你的 baseline 档设计要引。
44. **Titzer**（OOPSLA 2022）WebAssembly 的快速原地解释器；**Titzer**（CGO 2024）"Whose Baseline Compiler Is It Anyway?" 系统比较解释器与基线编译器的取舍。`[待核]` 后一篇我对年份和是否合著把握一般。这两篇是"要不要基线编译器档"这个问题上最新最直接的证据。
45. **V8 Liftoff → TurboFan** 的 WASM tier-up，以及 **Wasmtime 的 Winch + Cranelift** 双编译器。**结构上跟你最接近的现役系统**，Liftoff 那条尤其——它就是热度驱动的运行时提升，只是在 WASM 不在 EVM。这一条你必须正面处理，否则审稿人会问"你跟 Liftoff 差在哪"。
46. **Haas et al.**（PLDI 2017）— WebAssembly 规范论文。
47. **Jangda et al.**（USENIX ATC 2019）— "Not So Fast"，实测 WASM 与原生代码的性能差距。

## 最后：related work 结尾那段该说什么

上面这些摆完，审稿人会问"JVM 干了三十年的事，搬到 EVM 上新在哪"。建议专门留一段答这个，四个点都是真实存在、别人没处理过的约束：

- **跨层语义必须逐 gas 一致**——任何一层算出的 gas 与状态改动有一丁点偏差就是共识分叉，JVM 分层允许的浮点/时序差异在这里全不允许。
- **编译延迟落在区块执行预算里**——不是后台线程慢慢编就行，编译本身可能变成 DoS 面。
- **profile 是链上全局量**——调用频率对全网可见且各节点一致，这跟 JVM 的进程内私有 profile 根本不同：可以跨节点、跨重启复用，也意味着攻击者能看见并操纵你的提升阈值。
- **缓存按 code hash 持久化**——合约字节码不可变，编译产物可以跨区块跨节点长期复用，这是 EVM 比通用语言运行时有利的地方。

第四点顺手把 22（CKB-VM）和 5（evmjit）串起来了：它们都做了 code-hash 缓存但都没做热度提升，这正好是你那句 "the first" 的落点。

## 一、区块链虚拟机

### 1.1 EVM 执行引擎（工业实现，直接相邻）

- **go-ethereum `core/vm`** — switch dispatch 的纯解释器，事实上的参考实现，做 baseline 对比绕不开。
- **revm** — Rust 写的 EVM 解释器，Reth / Foundry / 大量 L2 在用，目前性能最好的纯解释器。
- **evmone (baseline)** — C++ 实现，computed-goto 分发 + 预先做 jumpdest 分析，追求低启动开销。
- **evmone (advanced)** — 同一代码库的第二档，按 basic block 预计算 gas 和栈高度需求、做指令融合；走哪档编译期静态决定。
- **evmjit** — Bylica 2016 年的 LLVM-based EVM JIT（cpp-ethereum 后端），EVM 上编译执行的第一次认真尝试，按 code hash 缓存产物。
- **SmartVM**\* — 上面说的那个，解释器 + evmjit 的热度触发切换，你的 related work 必须点名。
- **revmc** — Paradigm 资助、基于 LLVM 的 revm 编译器，JIT 与 AOT 两种用法，但不按热度提升。
- **evm-mlir / LambdaClass**\* — 用 MLIR/LLVM 把 EVM bytecode 编成 native 的另一条 AOT 线。
- **Monad**\* — 并行执行 + 自研 EVM 实现，公开材料里提过编译执行方向，细节我不确定，引之前看下他们最新的技术文档。
- **Nethermind / Besu / Erigon** — 各自的解释器实现，凑客户端多样性的背景句可以用一句话带过。
- **EOF (EIP-3540 / 3670 / 4200 / 4750)** — 代码分段、静态跳转、禁用动态 jump，让提前分析和编译变得可行；这是生态自己在往"好编译"方向走的证据，对你是顺风material。

### 1.2 让 EVM 可编译的前置分析（学术，你的优化档会用到）

- **KEVM**（Hildenbrandt et al., CSF 2018）— K 框架下的完整 EVM 形式语义，你论证"编译产物语义等价"时的参照系。
- **Hirai**（WTSC/FC 2017）— Lem/Isabelle 里的 EVM 定义，同上，更早。
- **Gigahorse**（Grech et al., ICSE 2019）— EVM 字节码的声明式反编译，重点是从动态跳转里恢复 CFG 和函数边界。
- **Elipmoc**（Grech et al., OOPSLA 2022）— Gigahorse 的后继，上下文敏感的 CFG 恢复，精度显著更高。
- **EthIR**（Albert et al., ATVA 2018）— 把 EVM 字节码抬到基于规则的中间表示做高层分析。
- **Oyente**（Luu et al., CCS 2016）— 符号执行分析 EVM 字节码，CFG 构造那套的起点，历史引用。
- **Securify**（Tsankov et al., CCS 2018）— 依赖关系推导 + 合规/违规模式匹配的字节码分析。
- **Synthesis of Super-Optimized Smart Contracts Using Max-SMT**（Albert, Gordillo, Rubio, Schett, CAV 2020）— 用 Max-SMT 做 EVM basic block 的超优化，和你优化档的收益上界直接相关。
- **ebso**\*（Nagele & Schett）— EVM 字节码超优化器，出处我记不准，核实下venue。
- **GASTAP / GASOL**\*（Albert et al.）— EVM gas bound 的自动推导，你如果要论证"编译不改 gas"可以引。
- **Broken Metre**（Perez & Livshits, NDSS 2020）— 实证 gas 定价和真实执行时间严重脱节；这是你 motivation 里最好用的一条：gas 不是时间的代理，所以"哪些合约值得编译"必须靠实测热度，不能靠 gas。

### 1.3 profile-guided 的前提证据（motivation 段的弹药）

- **Analyzing Ethereum's Contract Topology**（Kiffer, Levin, Mislove, IMC 2018）— 链上合约代码大量重复、调用极度集中在少数合约；这条直接支撑"按调用频率提升"的设计前提。
- **An exploratory study of smart contracts in the Ethereum blockchain platform**（Oliva, Hassan, Jiang, EMSE 2020）— 绝大多数合约几乎没有交易，极小一部分吃掉绝大部分调用量，同上，是更细的版本。

这两条你一定要引，不然审稿人会问"你凭什么假设有 hot contract"。

### 1.4 并行与投机执行（相邻但不冲突，正常摆）

- **Adding Concurrency to Smart Contracts**（Dickerson, Gazzillo, Herlihy, Koskinen, PODC 2017）— 这条线的开山，矿工用投机并发执行、生成 happens-before 让验证者复用。
- **Block-STM**（Gelashvili et al., PPoPP 2023）— 乐观并行 + 多版本内存 + 按依赖动态重执行，Aptos 在用。
- **Forerunner**（Chen et al., SOSP 2021）— 基于约束的投机预执行，利用以太坊交易的重复结构提前算好结果；这条对你特别有用，因为它同样是"用历史/运行时信息加速执行"，但优化的是 what to execute 而不是 how to execute，正好衬托你的定位。

### 1.5 Move VM

- **Move: A Language With Programmable Resources**（Blackshear et al., Diem 技术报告）— 语言与 VM 设计，线性资源类型。
- **Resources: A Safe Language Abstraction for Money**（Blackshear et al., arXiv 2020）— 资源抽象的形式化陈述。
- **The Move Prover**（Zhong et al., CAV 2020）和 **Fast and Reliable Formal Verification with the Move Prover**（Dill et al., TACAS 2022）— 配套验证器。
- 对你的意义：Move 字节码是强类型、有 bytecode verifier、无任意地址动态分发的，**天然比 EVM 好编译**；写一句"Move 把编译难题挪到了语言设计层，EVM 没有这个奢侈"，正好反衬你要处理动态跳转。Aptos 那边的 Move-to-native 编译工作\* 我不确定现在到哪一步了，引之前查一下。
- **Sui 的 Move VM 分支** — object-centric 的执行模型和重做的 gas 计量，可以一句话带。

### 1.6 WASM 合约链（这块对你最有参考价值）

- **Bringing the Web Up to Speed with WebAssembly**（Haas et al., PLDI 2017）— WASM 本体，背景引用。
- **Not So Fast**（Jangda et al., USENIX ATC 2019）— WASM 对 native 的实测差距与原因，你做"编译到底能拿多少"的预期管理时有用。
- **ewasm** — 以太坊那次流产的 WASM 替换尝试，理由是"换个 VM 就能白嫖成熟 JIT 基建"，值得一句，因为它代表了和你相反的路线选择。
- **CosmWasm** — 跑在 Wasmer 上，**有 "pinned contracts" 机制：把指定合约的编译产物常驻内存**。这是最接近你的工业先例，但热合约是治理/配置手工指定的，不是运行时 profile 出来的——这句对比一定要写进去。
- **NEAR** — 用 Wasmer Singlepass，按 code hash 缓存编译产物；**选单遍编译器正是为了限住编译时间**。
- **Substrate / Polkadot** — `wasmi` 解释器和 `wasmtime`(Cranelift) 编译两种执行方式，选哪种是配置决定的，和 evmone 一样是静态二选一；PVF 预检查 + 编译产物缓存那套也值得一提。
- **PolkaVM**\* — Koute 的 RISC-V VM，主打线性时间的单遍 recompiler；我印象里社区讨论过加优化档，但具体状态不确定，核实。
- **Fizzy** — evmone 团队做的 WASM 解释器，为确定性和低启动开销刻意不做 JIT；同一批人在两个 VM 上做了同样的取舍，这个细节写进 related work 很有说服力。

### 1.7 其他链的 VM（各一句，凑广度）

- **Solana rbpf** — eBPF 变体，程序加载时 JIT 并缓存；又一个解释器/JIT 并存但静态选择的例子。
- **CKB-VM**\*（Nervos）— RISC-V，有解释器、汇编解释器和 AOT 多种模式。
- **Arbitrum Nitro**（以及 Kalodner et al., USENIX Security 2018）— 正常路径跑 native，只有争议仲裁时才切到 WAVM 解释执行；**按场景而非按热度选执行策略**，是个漂亮的对照。
- **zkSync EraVM** — 为了证明成本而改成寄存器式 VM，Solidity/Yul 经 LLVM 编到 EraVM；"为不同目标函数选不同执行策略"的另一个方向。
- **FuelVM** — 解释器，凑一句广度足够。

## 二、经典 tiering（背景铺垫）

### 2.1 起源：自适应重编译

- **An Efficient Implementation of SELF**（Chambers, Ungar, Lee, OOPSLA 1989）— SELF 的实现，定制化编译的起点。
- **Reconciling Responsiveness with Performance in Pure Object-Oriented Languages**（Hölzle & Ungar, TOPLAS 1996；OOPSLA 1994 版）— **这是你这篇的祖宗论文**：用便宜的非优化编译器先跑、按调用计数识别热方法再重编译，你的段落应该从这里起笔。
- **Optimizing Dynamically-Dispatched Calls with Run-Time Type Feedback**（Hölzle & Ungar, PLDI 1994）— profile-guided 的原型：用运行时类型反馈指导内联。
- **Debugging Optimized Code with Dynamic Deoptimization**（Hölzle, Chambers, Ungar, PLDI 1992）— deoptimization 机制；你如果做任何投机优化就必须引它。
- **Efficient Implementation of the Smalltalk-80 System**（Deutsch & Schiffman, POPL 1984）— inline cache 的原始出处。
- **Polymorphic Inline Caches**（Hölzle, Chambers, Ungar, ECOOP 1991）— PIC，profile 信息的经典载体。

### 2.2 提升策略本身（你最该正面对齐的）

- **Adaptive Optimization in the Jalapeño JVM**（Arnold, Fink, Grove, Hind, Sweeney, OOPSLA 2000）— **成本收益模型决定"什么时候、提升到哪一档"**，你那个"按调用频率"的策略应该明确定位成它的简化/特化版本，否则审稿人会说你的 policy 太土。
- **A Survey of Adaptive Optimization in Virtual Machines**（Arnold, Fink, Grove, Hind, Sweeney, Proc. IEEE 2005）— 这个领域的综述，背景段落一句话引它最省字数。
- **Design, Implementation and Evaluation of Adaptive Recompilation with On-Stack Replacement**（Fink & Qian, CGO 2003）— OSR；EVM 调用都很短，你大概率**不需要** OSR，但要主动说明为什么不需要（只有长循环合约才会成问题），这条是那句话的落脚点。
- **Continuous Program Optimization**\*（Kistler & Franz, TOPLAS 2003）— 持续在线重优化，可选。

### 2.3 生产级多档 VM（工业对照）

- **HotSpot C2**（Paleczny, Vick, Click, JVM Symposium 2001）— 服务端优化编译器，SSA + 全局调度。
- **HotSpot C1**（Kotzmann et al., ACM TACO 2008）— 客户端快速编译器；C1→C2 加调用计数与回边计数就是 HotSpot 的分层编译，和你的两档结构最像。
- **V8: Ignition → Sparkplug → Maglev → TurboFan** — 字节码解释器、无优化 baseline 编译器、中间档、全优化档，靠 feedback vector 驱动升档。**四档**这件事你要提前应对："为什么你只有两档"必须在论文里有答案。
- **JavaScriptCore: LLInt → Baseline → DFG → FTL** — 另一个四档设计，档位切换阈值和 OSR 进出的工程细节公开得很充分。
- **.NET Tiered Compilation** — tier0 快速编译 + 调用计数提升到 tier1，.NET 8 起还有 dynamic PGO；**精神上离你最近的工业系统**，值得单独一句。
- **Android ART** — 解释器 → JIT → **用运行时采集的 profile 做 AOT**（baseline profile / dex2oat），profile 还能跨进程跨设备分发。这条对你极有价值：链上所有节点跑同一份工作负载，profile 天然可以持久化甚至共享，ART 就是这个做法的先例。
- **HHVM**（Adams et al., OOPSLA 2014）— region-based JIT，先跑 profiling 档再按请求量重翻译到优化档，服务端长驻场景下的分层。

### 2.4 trace JIT 与替代路线（说明你为什么不走）

- **Dynamo**（Bala, Duesterwald, Banerjia, PLDI 2000）— 透明的运行时二进制优化，用 MRET 启发式识别热 trace。
- **HotpathVM**（Gal, Probst, Franz, VEE 2006）— 从热循环起步的 trace JIT。
- **TraceMonkey**（Gal et al., PLDI 2009）— trace 上做类型特化。
- **LuaJIT**（Mike Pall）— 工业界最成功的 trace JIT，无论文但可引实现。
- **PyPy 元追踪**（Bolz, Cuni, Fijalkowski, Rigo, ICOOOLPS 2009）— 追踪解释器本身而不是程序。
- **One VM to Rule Them All**（Würthinger et al., Onward! 2013）与 **Practical Partial Evaluation**（Würthinger et al., PLDI 2017）— Truffle/Graal，**用部分求值从解释器自动导出编译器**。审稿人一定会问"你为什么不直接对你的 EVM 解释器做 Truffle 式部分求值"，这两条是你回答那个问题的锚点。

### 2.5 编译时间作为受限资源（这块能直接支撑你的威胁模型）

- **Liftoff → TurboFan**（V8 的 WASM 分层）— 单遍 baseline 编译器保证启动延迟有界，后台再升到优化档；结构上和你要做的几乎一模一样，只是不在共识环境里。
- **SpiderMonkey Baseline → Ion**（WASM 与 JS 两侧）— 同上的另一个实现。
- **Wasmer Singlepass / Cranelift** — 明确以"编译时间可预测"为目标的后端选择，NEAR 选它就是这个原因。
- 这里有一句你该自己写进 related work 的话：上面所有系统里，**编译时间只影响延迟，不影响正确性**；在链上它是一个不计量的资源，攻击者可以部署一个编译起来极贵的合约来打你。据我所知没人在 EVM 上处理过这个，这可能比 tiering 本身更是你的贡献点。

## 一、EVM 执行引擎：必须点名并划清界限的

- **evmjit** (Bylica, 2016, ethereum/evmjit)：把整段 EVM bytecode 经 LLVM 编译成原生码、按 code hash 缓存，是 EVM 上第一个真正的运行时编译尝试，因编译开销对一次性调用不划算而被弃用。
- **go-ethereum 的 JIT EVM 实验**（`--jitvm`，2016–2017 年间引入又移除）〔具体版本号待核〕：geth 曾短暂提供 JIT 后端与指令融合优化，后以复杂度换不来收益为由删除。
- **evmone** (ethereum/evmone)：C++ 实现，baseline 用 computed-goto 跳转表并预计算基本块的 gas/栈校验，advanced 预解码成基本块 IR 并做指令融合，两档由构建/配置静态选定。
- **revm** (bluealloy/revm)：Rust 写的模块化 EVM 解释器，是 reth、Foundry 等工具链的事实标准执行核。
- **revmc** (DaniPopes/revmc)：基于 LLVM 的 EVM 编译器，挂在 revm 上，AOT 和 JIT 两种模式都支持，但触发时机与合约被调用的频次无关。
- **Monad 的 EVM 编译器** (monad-vm / monad-compiler)：高性能 EVM 链，公开材料描述为把合约编译到原生码并保留解释器兜底〔触发时机是部署时还是首次调用，待你核实原文〕。
- **MegaETH**：实时出块方向的 EVM 链，公开设计文档里明确讨论过解释执行是瓶颈、以及对热点合约做 JIT/AOT 编译〔具体到什么程度待核〕。
- **Nethermind / Besu / Erigon+Silkworm**：主流非 geth 执行客户端，各自的 EVM 都是纯解释器（Besu 跑在 JVM 上、Nethermind 跑在 CoreCLR 上，宿主 JIT 不等于 EVM 层 tiering，这点值得在段落里点一句）。
- **EVM Object Format (EIP-3540/3670/4200/4750)**：给 EVM 引入代码分段、部署时验证和静态相对跳转，消掉动态 JUMPDEST，是原生编译的重要前提条件。
- **precompiles**：Ethereum 用手工原生实现替换少数高频昂贵操作（椭圆曲线、哈希），可以当成 EVM 上最早、最粗粒度的"手动提升"。

## 二、EVM 相关的学术工作

- **Ethereum Yellow Paper** (Wood, 2014)：EVM 的形式化规范，栈式机、gas 计量和状态转移函数的原始定义。
- **KEVM: A Complete Formal Semantics of the EVM** (Hildenbrandt et al., CSF 2018)：用 K 框架写出可执行的 EVM 完整语义，可直接导出解释器并做一致性测试。
- **Forerunner: Constraint-Based Speculative Transaction Execution for Ethereum** (Chen et al., SOSP 2021)：在 mempool 阶段预执行交易并把结果按约束记忆化，正式执行时退化成快速重放——是 EVM 上另一条"用运行时观察换执行速度"的路线，跟你正交但必须提。
- **Adding Concurrency to Smart Contracts** (Dickerson, Gazzillo, Herlihy, Saraph, PODC 2017)：矿工用抽象锁做投机并发执行并产出可串行化调度，验证者按调度重放。
- **Block-STM** (Gelashvili et al., PPoPP 2023)：乐观并行执行 + 多版本内存 + 动态依赖检测，把区块内的固定顺序从约束变成优势。
- **Broken Metre: Attacking Resource Metering in EVM** (Perez & Livshits, NDSS 2020)：实证说明 gas 成本与真实执行时间严重脱节，可以拿来支撑"gas 不是好的热度代理、需要真实 profile"。
- **Gigahorse** (Grech et al., ICSE 2019) 与 **Elipmoc** (OOPSLA 2022)：从 EVM bytecode 反编译出 CFG 和函数边界，处理动态跳转带来的控制流恢复难题——你的编译器前端面对的是同一个问题。
- **GASOL / Super-optimization of Smart Contracts** (Albert et al., TACAS 2020 及后续 TOSEM)：用 SMT 做 EVM 字节码块级超优化以降低 gas，属于静态、部署前的优化。
- **ebso: EVM Bytecode Super Optimizer** (Nagele & Schett)〔年份出处待核〕：同类的约束求解式字节码超优化。
- **An Exploratory Study of Smart Contracts in the Ethereum Blockchain Platform** (Oliva, Hassan, Jiang, EMSE 2020)：实证发现极小比例的合约承担了绝大多数调用量——这是你"热点合约存在"这个前提最直接的引用。
- **Understanding Ethereum via Graph Analysis** (Chen et al., INFOCOM 2018)：对合约调用图做度分布分析，同样显示重尾/幂律的调用集中现象。
- **Arbitrum: Scalable, Private Smart Contracts** (Kalodner et al., USENIX Security 2018)：链下执行 + 争议裁决，是把执行从 L1 解释器里搬走的另一类思路。

## 三、其他区块链虚拟机

- **Move: A Language With Programmable Resources** (Blackshear et al., 2019)：带资源类型和字节码验证器的合约语言与 VM，Diem/Aptos/Sui 的共同基础。
- **The Move Prover** (Zhong et al., CAV 2020)：Move 合约的形式化验证工具链。
- **Robust Safety for Move** (CSF 2022)：Move 字节码验证器安全性质的形式化论证。
- **Aptos / Sui 的 MoveVM**：生产环境的 Move 解释器，性能路线押在并行调度（Block-STM）和对象模型上，而非执行层编译。
- **Solana rbpf** (solana-labs/rbpf)：SBF 字节码 VM，同时提供解释器和 x86-64 JIT，但用哪个是配置决定的，不看调用热度；**Firedancer** 另行实现了自己的 VM 与 JIT。
- **ewasm / evm2wasm**：已废弃的 Ethereum WASM 执行层提案，含把 EVM 语义转译到 WASM 的工具。
- **Bringing the Web up to Speed with WebAssembly** (Haas et al., PLDI 2017)：WASM 的设计与形式语义，解释为何它天然适合快速 AOT 编译。
- **CosmWasm**：Cosmos 上基于 Wasmer 的合约运行时，用中间件注入确定性 gas 计量并缓存编译模块。
- **NEAR 合约运行时** (near-vm，Wasmer singlepass 分支)：合约 WASM 在部署/首次执行时 AOT 编译并按 code hash 持久缓存，编译与执行热度无关。
- **Arbitrum Stylus**：允许 WASM 合约与 EVM 合约共存，WASM 合约在 activation 时 AOT 编译成原生码并用 "ink" 计量——生产环境里最接近"合约原生编译"的系统。
- **Substrate/Polkadot runtime**：用 Wasmtime 执行链上 runtime WASM 并缓存编译产物。
- **PolkaVM** (Parity)：改用 RISC-V 作为合约字节码，靠 recompiler 直接产出 x86-64 原生码，论点是 RISC-V 比 WASM 更适合低延迟重编译。
- **Cairo – a Turing-complete STARK-friendly CPU architecture** (Goldberg, Papini, Riabzev, ePrint 2021)：为可证明计算设计的 VM 架构，优化目标是证明成本而非执行速度。
- **Not So Fast: Analyzing the Performance of WebAssembly vs. Native Code** (Jangda et al., USENIX ATC 2019)：量化托管字节码相对原生码的开销来源，可以借来给"解释器差多少"做定量背景。

## 四、经典 tiering（背景铺垫）

**祖宗级：**
- **An Efficient Implementation of SELF** (Chambers, Ungar, Lee, OOPSLA 1989) 与 **Customization** (PLDI 1989)：动态类型语言的运行时特化编译的起点。
- **Optimizing Dynamically-Typed OO Languages With Polymorphic Inline Caches** (Hölzle, Chambers, Ungar, ECOOP 1991)：用运行时观察到的类型反馈驱动后续优化。
- **Debugging Optimized Code with Dynamic Deoptimization** (Hölzle, Chambers, Ungar, PLDI 1992)：deoptimization 的原始论文，让"先乐观编译、错了退回解释器"成为可能。
- **Reconciling Responsiveness with Performance in Pure OO Languages** (Hölzle & Ungar, TOPLAS 1996)：Self 的自适应重编译系统，按调用计数触发提升，是你这套机制最直接的思想来源。

**多级重编译的标准参考：**
- **Adaptive Optimization in the Jalapeño JVM** (Arnold, Fink, Grove, Hind, Sweeney, OOPSLA 2000)：采样式热方法识别 + 成本收益模型决定提升到哪一级优化，是"tiered, profile-guided recompilation"最经典的完整系统，你的设计对照基本就是它。
- **A Survey of Adaptive Optimization in Virtual Machines** (Arnold et al., Proc. IEEE 2005)：该领域的综述，适合一句话带过整个背景。
- **Design, Implementation and Evaluation of Adaptive Recompilation with On-Stack Replacement** (Fink & Qian, CGO 2003)：OSR 的系统性设计与评估——如果你的合约执行会在长循环中途提升，这条必引。
- **Flexible On-Stack Replacement in LLVM** (D'Elia & Demetrescu, CGO 2016) 与 **A Modular Approach to OSR in LLVM** (Lameed & Hendren, VEE 2013)：在 LLVM 上实现 OSR 的工程方案，跟 revmc 走 LLVM 的情况直接对口。

**生产 VM 的分层结构：**
- **The Java HotSpot Server Compiler** (Paleczny, Vick, Click, JVM Symposium 2001)：C2 的 sea-of-nodes 设计与基于 profile 的激进内联。
- **Design of the Java HotSpot Client Compiler for Java 6** (Kotzmann et al., TACO 2008)：C1 的设计，即 HotSpot 分层里的快速档。
- **HotSpot Tiered Compilation**（JDK 7+，`-XX:+TieredCompilation`）：解释器 → C1（含插桩档）→ C2 的五级结构，profile 由 C1 档收集后喂给 C2。
- **V8: Ignition → Sparkplug → Maglev → TurboFan**：四档 JS 执行栈，靠 feedback vector 和 interrupt budget 驱动提升、靠 deopt 退档，是当代最完整的分层样板。
- **Liftoff**（V8 的 WASM baseline 编译器，2018）：先用单遍快速编译器出码、后台再用 TurboFan 重编译热函数——部署模型（一段不可变字节码、首次执行延迟敏感）跟合约场景最像的一条。
- **JavaScriptCore 的四档**（LLInt → Baseline JIT → DFG → FTL）：Pizlo 的 *Speculation in JavaScriptCore* 是这套 OSR-in/OSR-out 机制最详细的公开描述。
- **SpiderMonkey**（Baseline Interpreter → Baseline JIT → Ion/Warp），配 **Fast and Precise Hybrid Type Inference for JavaScript** (Hackett & Guo, PLDI 2012)。
- **.NET CoreCLR tiered compilation + dynamic PGO**：tier0 快速出码并计数，热方法升 tier1；.NET 8 起 tier0 可插桩收集 profile 再驱动 tier1 优化，是"插桩档 → 优化档"这一模式的现代工业实例。
- **Android ART**：从 Dalvik 的 trace JIT 到 ART 的全量 AOT，再回到解释器 + JIT + 按设备 profile 做的 profile-guided AOT 混合体——这条"纯 AOT 退回分层"的演化弧线，正好是你想对 EVM 讲的故事。
- **The HipHop Virtual Machine** (Adams et al., OOPSLA 2014)：PHP 的 tracelet/region JIT；HHVM 后来的 RetranslateAll 用预热期 profile 统一重编译全部热代码，跟"从主网采 profile 再重编译"高度类比。

**trace / 元编译路线（对照组）：**
- **Dynamo: A Transparent Dynamic Optimization System** (Bala, Duesterwald, Banerjia, PLDI 2000)：纯运行时的原生码到原生码热路径优化。
- **HotpathVM** (Gal, Probst, Franz, VEE 2006)：资源受限设备上按热循环触发的 trace 编译。
- **Trace-based JIT Type Specialization for Dynamic Languages** (Gal et al., PLDI 2009)：TraceMonkey，热循环 trace + 类型特化。
- **Tracing the Meta-Level: PyPy's Tracing JIT Compiler** (Bolz et al., ICOOOLPS 2009)：对解释器本身做 trace 的元 JIT。
- **One VM to Rule Them All** (Würthinger et al., Onward! 2013) 与 **Practical Partial Evaluation for High-Performance Dynamic Language Runtimes** (PLDI 2017)：Truffle/Graal 用部分求值把解释器自动变成优化编译器，是"不手写第二档"的替代方案，审稿人很可能问你为什么不走这条。

**解释器一侧与 profile 一侧：**
- **The Structure and Performance of Efficient Interpreters** (Ertl & Gregg, JILP 2003)：threaded code 与分支预测行为，解释 evmone baseline 那类优化的收益上限。
- **Efficient Interpretation Using Quickening** (Brunthaler, DLS 2010)：运行时改写字节码做特化，属于"零编译成本的轻量提升"。
- **A Fast In-Place Interpreter for WebAssembly** (Titzer, OOPSLA 2022)：Wizard，论证快速解释器在分层体系里仍有位置。
- **Whose Baseline Compiler Is It Anyway?** (Titzer, CGO 2024)〔出处待核〕：系统比较 baseline 编译器与解释器的取舍。
- **AutoFDO** (Chen et al., CGO 2016)：从生产环境采样 profile 反馈给 AOT 编译，无需插桩构建。
- **BOLT** (Panchenko et al., CGO 2019)：链接后用 profile 重排二进制布局；和 AutoFDO 一起支撑你"profile 可以来自真实线上负载"的论证。

## 1. EVM 执行引擎（工业实现）

- **go-ethereum (geth)** —— 参考实现，`core/vm` 是 switch dispatch 解释器加一遍 jumpdest 分析，所有人的 baseline。
- **evmone** —— C++ 实现，`baseline`（computed-goto 解释器）和 `advanced`（预处理成 basic block，逐块预算 gas 和栈高度需求、融合指令）两档，走哪档是配置期静态决定的。
- **evmjit**（Bylica, 2015）—— 基于 LLVM 的 EVM→native 编译器，可作为 cpp-ethereum/geth 后端，按合约 AOT 编译并用磁盘 object cache 缓存，是 evmone 的前身。
- **revm** —— Rust 解释器，Reth / Foundry / 各类模拟器的事实标准后端，纯解释执行。
- **revmc**（Paradigm）—— revm 的 LLVM 后端编译器，支持 JIT 和 AOT 两种模式，按合约编译、按 code hash 缓存产物。
- **evm-mlir / LambdaClass 系**（EF 资助的 EVM AOT 方向）—— 用 MLIR/LLVM 做 EVM 字节码到 native 的编译，定位和 revmc 同类。（条目名和归属请核实）
- **Besu（Java EVM）** —— 值得单列一句：它跑在 HotSpot 上，宿主层的分层编译对它免费生效，但热的是解释器循环本身，合约层面拿不到任何特化。这句话很适合放在你 related work 开头用来划清"宿主 JIT ≠ 合约 JIT"。
- **goevmlab**（Swende）—— 多客户端 EVM 差分 fuzzing 工具链，你要论证"新执行档不破共识"时，方法学上绕不开。

## A. EVM 执行引擎（工业实现为主）

- **evmjit**（Bylica, ~2016）— 最早的 EVM LLVM JIT，按合约整体编译成原生码并按 code hash 缓存，无分层、无热度判断，编了就一直用。
- **cpp-ethereum SmartVM** — 解释器与 evmjit 之间按执行计数切换的模式，达阈值后异步编译（见上，需核实）。
- **Nethermind IL-EVM** — 运行时把热点 EVM 字节码段编译成 .NET IL，带热度阈值和常见 opcode 序列的 superinstruction 替换（需核实）。
- **revmc** — revm 的 LLVM/Cranelift 后端编译器，AOT 与"按需 JIT"两种用法，但触发编译的是外部调用而非执行热度。
- **evmone baseline** — 带 JUMPDEST 预分析的直接分发解释器，逐条指令计 gas。
- **evmone advanced** — 预先把字节码切成基本块，把栈高度检查和 gas 扣减提升到块入口一次性完成；走哪一档在 VM 构造时静态决定。
- **go-ethereum core/vm** — 跳转表解释器，逐 opcode 分发，是几乎所有 EVM 性能论文的 baseline。
- **revm / reth** — Rust 解释器，当前事实上的性能基准实现，你的实验大概率要跟它比。
- **Hyperledger Besu EVM**（Java）— 解释器，但跑在 HotSpot 上，等于白拿了宿主层的分层编译；作为"分层发生在错误的抽象层"这个论点的例子很好用。
- **Nethermind / erigon-silkworm / ethereumjs / py-evm** — 各语言的解释器实现，一句话带过即可，用来支撑"single execution strategy"这个观察不是个例。
- **EOF（EIP-3540/3670/4200/4750）** — 分节、静态跳转、禁止动态 jumpdest，把 EVM 字节码的 CFG 恢复从难题降成常规问题；跟你的编译前端直接相关，值得单独一段。
- **evm-bench / Ipsilon 的 benchmark 套件** — EVM 实现间的横向性能测试，给你的 evaluation 提供可比数字。

## B. 其他链的 VM 与编译策略

- **Solana rBPF / SBF loader-v4** — 部署时把 SBF 字节码 AOT 编译成 x86-64 并缓存，编译时机由部署决定而非执行热度。
- **NEAR** — 用 Wasmer singlepass，明确牺牲代码质量换编译时间的可预测性，因为编译耗时本身是攻击面；这条直接支撑你"tier-0 不能阻塞出块"的设计动机。
- **CosmWasm** — Wasmer + 模块缓存，把常用合约 "pin" 在内存里避免重复编译；概念上是热度提升的一个粗粒度退化版本。
- **Arbitrum Stylus** — WASM 合约在 "activation" 阶段一次性 AOT 编译，之后固定；与 revmc 同属"编完就定"那一类。
- **Polkadot: wasmi → wasmtime → PolkaVM** — 从解释器到 Cranelift 再到基于 RISC-V 的线性时间 recompiler，整条演进线是"确定性约束下如何选编译策略"的好素材。
- **Move VM（Diem / Aptos / Sui）** — 栈式解释器 + 字节码验证器，字节码是强类型且已验证的，所以编译前端比 EVM 容易得多；作为对比很有说服力。
- **Move 语言白皮书**（Blackshear et al., 2019）— 资源类型与字节码格式的原始描述，引 Move VM 时配套。
- **Internet Computer / DFINITY** — wasmtime 加确定性指令计数，展示了在编译后代码里维持精确计量的工程做法，跟你"编译后 gas 必须逐 wei 一致"的问题同构。
- **FuelVM** — 寄存器式 VM，说明 EVM 的栈式设计本身是性能约束之一。
- **Fizzy / wasmi** — 为确定性执行而写的 WASM 解释器，用来说明区块链场景偏好解释器的理由。
