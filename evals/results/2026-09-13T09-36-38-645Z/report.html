# 二、顶会标准评估（Phase 3）

按流程，评分前先做 fatal-flaw 审计。**审计出的 MAJOR 缺陷叠了三条，按规则触发 CRITICAL 短路，所以我不给五维评分，直接给结论。**

### F-A：天花板没测过，而且我估算它很低 —— MAJOR

这是最重要的一条，请你认真看这段算术：

设该块串行执行耗时 $S$。一个几乎全是同池 swap 的块，**它的真实依赖就是全序的**——任何调度器，哪怕拿到完美预言机，也快不过 $S$。而 Block-STM 在这种块上大约落在 $0.8S \sim 0.9S$ 的吞吐（验证开销 + abort 开销），并不是你想象的"算力基本白烧"：Block-STM 有依赖追踪，tx j 因 tx i abort 时会**登记依赖并挂起**，而不是空转重跑。

所以完美预测在**最坏的块**上最多帮你拿回 10~25%，在 Block-STM 本来就跑得好的块上帮你拿回 **0%**。按主网真实区块分布加权，端到端可能就是个位数百分比。**然后你还要从这几个百分点里掏钱付 GNN 推理。**

我可能算错了——但"我可能算错了"正是你必须先测的理由。

### F-B：baseline 无效 —— MAJOR

「直接跟 Block-STM 原论文报的吞吐数字比」是**任何会议都会当场拒的**。原文跑的是 Move / Aptos 的合成负载（不同 VM、不同状态模型、不同硬件）`[UNVERIFIED]`，你跑的是 revm 重放主网区块。这不是"不够严谨"，是两组数字之间不存在可比性。

你必须在**同一份代码库、同一台 32 核机器、同一批区块**上跑 head-to-head。好消息是不用从零写：pevm(Rise)、grevm(Galxe)、Polygon 的 block-stm 都是开源的 Block-STM-for-EVM 实现 `[UNVERIFIED]`。

### F-C：推理预算 —— MAJOR

$n \approx 200$ 的块意味着 $O(n^2) \approx 4$ 万条候选边。整块 revm 执行也就几十毫秒量级，你要在**亚毫秒**内建图 + 推理才划算。单是 host-device 传输和 kernel launch 就要几百微秒。更根本的问题是：**生产节点没有 4090。** 你在用 GPU 算力换 CPU 算力，这笔账必须在论文里明算。

而且有个循环论证陷阱：要把 4 万条边剪到可控规模，最自然的剪枝就是"只考虑 to 地址相同的对"——那你已经在用那张哈希表了，GNN 只是在它的输出上做了个二次修饰。

### 新的一句话贡献

> 我们在真实主网区块上测出了乐观并行 EVM 执行的**调度天花板**，并给出一条预测器阶梯，指出这个天花板在哪一级被吃满、代价是多少——**推理开销计入总账**。

从"我有个方法"变成"我先测清楚这件事到底有多少可为空间"。后者是 measurement paper 的路子，**结论是正是负都能发**。

### Intro 五段式

**P1 · 背景钩子。** 并行执行已经是 EVM 吞吐的主战场：L1 gas limit 在抬、L2 在拼 TPS，主流实现（pevm、grevm、Polygon、Monad、Sei）清一色押注乐观并发控制。

**P2 · 张力 + gap。** 乐观是一场"冲突很少"的赌注。可真实主网不是低冲突负载——DeFi 活动高度集中在少数热点合约上，一个块可以几乎全是同一个池子的 swap。这场赌注在那种块上是输的。**但到底输掉多少，其中又有多少是可以拿回来的？这个数字没人公开测过。** ← 这就是 gap，而且它是个**测量型 gap**，不依赖你的方法成功。

**P3 · 动作。** 我们不急着再造一个预测器，先把天花板钉死：在重放的主网区块上装一个**完美冲突预言机**，测出任何调度器相对 Block-STM 能拿到的速度提升上界。然后走一条**代价递增的预测器阶梯**——仅 to 地址 → to + selector → 历史 access set 记忆化 → 字节码静态分析 → 学习型预测器——问两件事：天花板在第几级就被吃满，以及每一级的推理成本是多少。

**P4 · 发现（两个分支都能填）。**
- GNN 赢 → "学习确实有增量，这是它划算的预算区间"
- GNN 输 → "**一张几十行的记忆化表就吃满了全部天花板，EVM 调度不需要学习型预测器**"

第二个分支是个**有价值的负结果**，替整个领域省下力气，在系统/测量类会议上完全发得出去。**你现在的方案只有分支一能活，这就是它的结构性风险。**

**P5 · 贡献清单。**
1. 首次用预言机测出主网区块上相对 Block-STM 的调度 headroom
2. 预测器的**成本-精度 Pareto 前沿，且首次把推理开销记入总账**（前作普遍不收这笔钱）
3. **开源的重放框架 + 主网标注冲突数据集** ← 这是真资产，也正是你有把握的那块
4. revm 内的系统实现，与同代码库的 Block-STM 同机 head-to-head

### 三个即刻动作

1. **先查 grevm / pevm 到底有没有依赖图和 hint 机制。** 半天的事，但可能直接定生死。
2. **两周内把预言机实验跑出来。** 完美预测相对 Block-STM 能拿多少？**这个数字决定项目是否存在。** 在它出来之前一个字都别写。
3. **同时把那张 `(to, selector)` 哈希表 + access set 记忆化实现掉。** 这是你真正的基线。如果它就吃满了天花板——恭喜，你提前三个月知道了，而且手上还有一篇 measurement paper。

### 两个附带的技术点

**标签定义有坑，而且这个坑本身有研究价值。** read/write set 是**依赖执行顺序的**：tx i 改了某个 slot，可能让 tx j 走进不同分支、读到不同的 slot 集合。所以"真实冲突"离开具体调度并不是良定义的。标准做法是以规范串行序为准，但这意味着你的预测器学的是**某一个特定调度下的**冲突关系，换个调度可能就漏了。这值得论文里专门写一段——也是个真的研究点。
